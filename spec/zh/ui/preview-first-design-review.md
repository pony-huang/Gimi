# 预览优先的 UI 设计评审

核对日期：2026-11-07。读者：修改 Compose UI 的代理与开发者。

本文是 `AGENTS.md` 所链接的预览设计与审批流程的完整规范。准备草案时同时遵守 [Gimi 品牌造型](brand-styling.md)。本流程适用于 UI 变更；仅修改这些规范文档不需要 Compose 草案。

## 工作流程

- 小范围、局部 UI 调整（如间距、对齐、主题颜色或移动已有按钮）可以直接实现，无需单独设计草案、询问图片交付偏好或设计审批。范围或预期外观不清晰时，可以向开发者咨询是否直接实施；咨询是可选项，不是强制审批关卡。仍需维护已有预览并进行与风险相称的验证。
- 超出上述小调整的 UI 变更，必须先准备预览设计草案，再进入实现：使用 `@Preview @Composable`，配合假数据或固定样例，支持浅色与深色主题，呈现拟议布局、新状态及交互入口。
- 对需要草案的 UI 任务，开始时询问用户是否需要渲染设计图片以便远程评审，除非用户已表明该任务的偏好。必须等到回答后再选择图片交付分支；等待期间可继续准备草案。
- 用户需要图片时，渲染实际 Compose 草案，目视检查截图，并在请求设计审批前在对话中交付可查看的图片。图片应包含浅色、深色及相关变化状态，存放于 `temp/`。源文件、文件链接或编译成功均不能替代图片交付。无法渲染时，说明具体阻碍，并与用户商定替代方案。
- 用户不需要图片时，跳过渲染和图片交付，用简短说明呈现草案。拒绝图片不等于免除下述设计审批，除非用户明确表示豁免。
- 需要草案的变更，必须将草案交给用户评审；只有用户明确确认设计后，才可以开始实现，除非用户明确豁免此步骤。
- 草案应与生产接线隔离（暂不修改 ViewModel 或仓储）；批准后将其合入真实页面并接入状态，随后删除独立草案文件及仅为该草案引入的依赖。

## 交互连续性与动效

- 先将手感反馈转化为可观察的交互问题，再选择动画方案：检查输入响应、状态切换、布局变化及组件生命周期。时长和运动方式应适应具体场景；单纯延长时间不能保证流畅。
- 调整动效时，保留控件的信息表达和无障碍约定。视觉反馈、手势位置与已提交的业务状态可能需要分别表示；按交互需要决定同步和收敛方式，不预设它们必须以相同方式更新。
- 让相关内容、几何尺寸与生命周期的过渡保持协调。需要退场动画时，将离场内容保留到动画完成。针对实际交互，明确重复输入、中断、取消及外部状态更新的处理方式。
- 优先在所属组件或功能内调整。有当前复用需求时再扩展共享接口，并在暴露新类型前检查调用方兼容性和框架 API 限制。

## 完成与验证

批准后，保留生产代码中覆盖相关视觉与条件状态的 `@Preview` 样例，使用固定数据并支持浅色和深色。仅删除隔离草案及其专用依赖。按 `AGENTS.md` 执行与风险相称的编译和真机验证；本流程不新增自动化 UI 交互、布局或截图测试要求。

汇报完成前，说明适用分支（小调整或设计草案）、图片偏好与明确的设计批准／豁免、维护的预览及实际执行的验证。同一任务中已提供的图片偏好、批准或豁免持续有效，不重复询问。

验证证据应与结论匹配：预览验证静态状态，构建验证编译，部署验证交付。只有实际操作或查看受影响路径的录制后，才能报告动效和交互观感已验证。按变更选择有代表性的路径和中断场景，并明确尚未验证的行为。
