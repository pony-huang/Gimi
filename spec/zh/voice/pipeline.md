> 全链路，以及每个环节背后的取舍。主文档负责系统总览、对话方式、供应商矩阵与
> 改动检查清单；本文件承载各环节的原因、坑与跨模块契约。类名、常量和代码流程

## 端到端链路

### 入口与权限

语音入口申请麦克风权限，仅在已授权时启动；被拒绝则提示并收起页面。

- **返回与挂断不是一回事。** 系统返回键和左侧「回聊天」胶囊结束通话并
  **回到文字聊天**；页内「挂断」只结束会话，留在语音页待启动状态。两条路径要
  分开——把它们当成同一个才是真正的坑。

### 采集

用阻塞读取，块大小由设备决定；首采样时刻取自音频时钟，绝不来自回调。

- **分帧在检测器里，不在录音器里。** 检测器自己累积任意长度输入，凑满一帧才
  回调。正是这个保证让切句器可以放心断言帧长。别把分帧挪进录音器，也别把原始
  数据块直接喂给切句器。
- **绝不用回调到达时间做时间戳。** 到达时间会和实际播放错位，悄悄把回声消除
  弄失效。时间戳要从录音音频时钟取。

### 回声消除：硬件优先，软件兜底，二者互斥

设备支持就用硬件 AEC，否则跑软件消除器。绝不能两者同时开。

- **互斥而非叠加。** 重复消除会损伤近端语音、白白烧 CPU。改这条分支前先确认
  两层不会同时启用。
- **参考信号按硬件播放时钟计时。** 消除器由播放供数、由麦克风时间驱动，参考帧
  必须对齐音频时间戳。把出包时间、回调时间和硬件时钟混用是回声失效最常见的原因。
  播放与 AEC 采样率不同，帧几何是绑在一起的——改一端就得改另一端。
- **播放期回声门控常驻，且不依赖 AEC 是否真的消干净。** AEC 状态在会话建立和
  路由切换时归零；重新收敛期间残留回声在 VAD 眼里和真话没区别。那两处各开一个
  短固定窗口不够：它可能在首个播放包到达前就烧完，而长播报后半程的残留照样以
  原始概率进入切句器，触发开口，最终把助手自己的播报喂回 ASR，形成自激循环。
  全双工和级联共用检测器入口，所以一起中招。「常驻」指**每帧都判定**，不是
  一律压制：明显更响的近端人声仍要放行，否则播报期无法打断，全双工退化成半双工。
  被压到 0 的帧仍喂给切句器和上行预滚环，预滚音频、VAD 状态和打断前导都不丢。
- **撤防看 `player.playing`，不看播放参考电平。** 参考电平由播放位置锚定时钟，
  锚点漂移时会虚假返回静音，拿它当开关等于在最响处撤防。回声基线来自麦克风实测，
  不依赖播放时钟，才可靠。
- **`playing` 变 false 后仍有声学尾音。** 硬件队列排空后，房间混响、扬声器余振和
  AEC 残留都还在——尾音期要继续过门控，否则「播着播着突然录到声音」恰好落在
  撤防那一帧。上行播放判定也必须同时看播放状态与尾音风险，否则尾音被全量上行，
  服务端 VAD 又会判成一次用户开口：这是第二条独立的自激路径。
- **静音停的是 VAD 喂入，不是麦克风。** 静音不停录音流、不停回声处理；它停掉
  喂给检测器的数据，于是开口永远不触发——**静音期间无法用开口打断**。开口
  内部的第二道判断再做一层保险。设计意图是：非静音时麦克风全程不停，因此说话
  天然可打断，不需要额外的「监听窗口」。

取舍：首播延后打断、播放期需连续确认帧，会让弱声打断迟钝且需真机校准；无条件
压制能彻底杜绝自激，但会退化成半双工。

### VAD 与切句

- **每帧重建输入张量。** 复用会让输入恒为零，表现为「永远检测不到说话」。
- **单句上限在两处，行为不同。** 切句器是截断后交出音频，下游输入校验是抛错。
  因为切句器已经先截断，真正可达的只有截断，所以超长独白会被切成多轮，绝不报错。
  抛错那道纯粹是防御，防的是将来有人绕过切句器直接灌原始音频。

### 上行与识别

识别请求体是整段话语的完整 PCM，不是持续流。各供应商传输方式完全不同——
新增供应商时记得更新此表：

| 供应商 | 传输 | 分片 | 编码 |
|---|---|---|---|
| DashScope（`qwen-audio`） | WebSocket | 约 1 s 一片 | 裸 PCM16 |
| MiniMax（`minimax-speech`） | HTTP multipart | 整段一次 | WAV |
| MiMo（`mimo-speech`） | HTTP chat-completions | 识别整段一次；合成 SSE | Base64 WAV 上行、PCM16 下行 |
| OpenAI 兼容（`deepseek`/`openai`/`kimi`/`glm`） | HTTP chat-completions | 整段一次 | Base64 WAV |
| OpenAI 专用（`openai-speech`） | HTTP multipart | 整段一次 | WAV |

- **DashScope 的 `finish-task` 必须带空 input**；非空会返回 `InvalidParameter`。
- **流式模型不接受中间结果与去口吃标志**；多传会让整段请求白跑。流式靠模型 ID 选择。
- **空结果意味着不生成。** 只有最终结果成为本轮输入，中间结果只刷界面。空结果
  回到待听、不回答、不占上下文——这就是咳嗽换不来一段回答的原因。
- **MiMo 的协议保持独立。** 它虽走 chat-completions，但音频是 data-URI、语种
  选项是厂商专属、合成文本放在 assistant 消息里、音色表也自成一份。请求形状
  确实不同——别并回 OpenAI 兼容路径。没有流式适配器的供应商退化为一次性识别、
  只发一个最终结果，调用方无需分支。

### 生成

- **把当前问题作为末尾 USER 折进 history。** 接口只在 history 以用户结尾时才
  启动回答；先发旧 history 再单独发当前问题，会在「上一句没听到任何回答」时
  重放上一轮的未答问题——踩过的坑。
- **级联语音路径无工具，三重保证：** 模型断言工具列表为空、指令里明写不具备工具、
  不传工具配置。
- **提示词是两层：** 可替换的人设 + 始终叠加的固定输出底线（朗读友好的句子、
  禁 Markdown、用用户语言回复）。预设每轮重读，通话中途切换下一轮生效；同一份
  预设同时驱动级联与原生实时。
- **助手模式全自动批准工具。** 需要确认的工具照常声明，但运行期一律按已确认答复——
  语音场景没有弹窗的位置。

### Chatbot 持久化

Chatbot 各入口共享 chatbot 分区里的同一个会话。真正要紧的行为差异：

- **级联**每轮读恢复的历史作为上下文。
- **原生实时**只写不读——绝不把历史注入模型上下文；每次起呼与重连都是全新上下文，
  历史只存在于持久化会话里。
- **被打断的轮丢掉半句回答。** 打断、取消、断线或关闭时，只写用户侧已定稿话语，
  被截断的回复丢弃。写入失败只告警不中断：通话继续，该轮只是没落盘。

### 合成与播放

合成优先用会话式（当前仅一家供应商支持双向），否则退化为逐句一次性合成。

- **先取消会话再关闭**，否则服务端会继续合成并计费。取消是协议级消息，不是
  客户端单方面断开。
- **以设备播放为准、而非服务端回合结束来更新「已听文本」。** 只有真正播出的音频
  才算已听；比较时单位要一致——播放头位置数的是帧、已写字节数的是采样数，
  仅单声道相等，改多声道必须同步修这个比较。
- **播放串行。** 跨网络分块保留残余字节，新段开始前断言没有活动轨道，否则段与段
  会互相穿插。
- **播放循环跑在非主线程。** 主线程上的状态更新和路由回调会与音频写入争抢，
  可见症状是实时录音掉帧。

### 打断

三个独立触发源、效果一致（停播 + 取消生成 + 清字幕）：本地开口检测（主路径——
人声一起就立即取消生成，不等下一次识别结果，免得为一段马上丢弃的回答付费）、
后端打断事件、播放代次失效。目前没有手动停止播报的控件，打断只能靠说话。

### 四个典型分支

把链路串成时序，比逐段读更容易建立整体感。

**① 正常一轮**

```text
开口 → speechStarted()：revision++ / 停播 / 取消旧回答 / phase=Listening
停口 → onUtterance → recognize() → phase=Transcribing；中间结果只刷界面，最终结果是输入
识别非空 → cancelAndJoin 旧 reply → phase=Thinking / revision++ / responseText 清空
生成合成 → 文本增量追加；音频段串行播放
首字节落设备 → phase=Speaking / speakingText=该句
该句播完 → spokenText += 该句 / phase=Thinking
段流关闭 → playback.join() → phase=Listening → finishTurn()
```

**② 空识别轮**：最终结果为空白（咳嗽、噪声）→ 直接回待听。不生成、不占上下文、
不消耗模型额度。

**③ 被打断轮**：说话阶段用户开口 → 开口检测抢先，停播、取消生成、清当前句，
回待听。已播完的句子留在「已听上下文」里；未播完的部分在 Chatbot 里直接丢弃。

**④ 失败与重试**：任意环节失败 → 停录音、复原路由、标记会话失败，UI 与会话仍在。
重试会重建录音流和整套 DSP 再走一次启动，而不是只恢复播放。

### 助手语音表达

通话控制器在所有链路中都选 chatbot 后端；保留的助手后端使用助手指令与共用的
语音表达契约，忽略 Chatbot 预设。回答结论优先、自然短句，需要动手时讲完当前一步后
等待，明显耗时的任务简短预告，尊重详细解释要求；代码、文档与链接通过工具交付
并语音简述结果，无法交付时说明限制。
